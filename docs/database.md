# Base de datos — JuampyZel

El sistema utiliza **Supabase (PostgreSQL)** como sistema de gestión de base de datos,
reemplazando la implementación anterior en MySQL.

## Archivo de base de datos

| Archivo | Descripción |
|---------|-------------|
| [`.supabase/schema.sql`](../supabase/schema.sql) | Esquema completo: tablas, constraints, índices, vistas, funciones (RPC), trigger, RLS y datos semilla. Aplica una sola vez. |

## Entidades y tablas

| Entidad | Tabla | Descripción |
|---------|-------|-------------|
| Usuario | `usuario` | Usuarios del sistema con autenticación. Incluye `rol` (`TEXT` con CHECK) y `estado` (`BOOLEAN`). |
| Categoría | `categoria` | Clasificación de productos. |
| Producto | `producto` | Helados y productos de la heladería. |
| Sucursal | `sucursal` | Locales físicos de venta. Cada sucursal tiene un responsable (`id_responsable`) que referencia a un usuario con rol `ENCARGADO_SUCURSAL`. Un encargado solo puede estar a cargo de una única sucursal. |
| Cliente | `cliente` | Clientes que compran en sucursales. |
| Tienda | `tienda` | Negocios externos que solicitan abastecimiento. |
| Inventario | `inventario` | Stock de productos por sucursal. Un producto solo tiene un registro por sucursal. |
| MovimientoInventario | `movimiento_inventario` | Historial de entradas, salidas y ajustes de stock. |
| AlertaStock | `alerta_stock` | Alertas de productos con bajo stock. |
| Venta | `venta` | Transacciones de venta en sucursales. |
| DetalleVenta | `detalle_venta` | Líneas detalladas de una venta. |
| Pedido | `pedido` | Pedidos realizados por tiendas. |
| DetallePedido | `detalle_pedido` | Líneas detalladas de un pedido. |
| HistorialPedido | `historial_pedido` | Trazabilidad de cambios de estado de pedido. |

## Tipos de columna (PostgreSQL vs MySQL)

| MySQL | PostgreSQL |
|-------|------------|
| `INT`/`BIGINT` AUTO_INCREMENT | `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| `DATETIME` (default `CURRENT_TIMESTAMP`) | `TIMESTAMPTZ` (default `NOW()`) |
| `TINYINT(1)` / `BOOLEAN` | `BOOLEAN` |
| `ENUM(...)` | `TEXT` + `CHECK (... IN ...)` |
| `DECIMAL(10,2)` | `NUMERIC(10,2)` |
| `ON UPDATE CURRENT_TIMESTAMP` | trigger `set_fecha_actualizacion()` (tabla `inventario`) |

## Vistas

El esquema define vistas que simplifican las consultas con joins y agregaciones
utilizadas por el backend:

- `vista_productos`, `vista_productos_activos`
- `vista_stock_producto` (agrega stock por producto y expone `bajo_stock`)
- `vista_catalogo_productos` (productos activos con `stock_disponible` para el portal Tienda)
- `vista_ventas`, `vista_pedidos`, `vista_historial_pedido`
- `vista_movimientos`, `vista_alertas` (con `estado_orden` para ordenamiento)

## Funciones (RPC)

Las operaciones atómicas y los reportes se ejecutan como funciones `plpgsql`
(`SECURITY DEFINER`, `search_path = public`) y se invocan desde el backend:

| Función | Propósito |
|---------|-----------|
| `registrar_venta` | Crea la venta, su detalle y descuenta stock en una transacción. |
| `registrar_pedido` | Crea el pedido, su detalle e historial `PENDIENTE` en una transacción. |
| `actualizar_estado_pedido` | Actualiza el estado y registra el historial. |
| `registrar_movimiento_inventario` | Actualiza stock y registra el movimiento. |
| `ajustar_stock_total` | Reparte el stock total entre sucursales y registra los ajustes. |
| `generar_alertas_stock` | Genera alertas de stock bajo sin duplicar pendientes. |
| `reporte_ventas_resumen`, `reporte_pedidos_resumen`, `reporte_productos_resumen`, `reporte_inventario_resumen`, `reporte_dashboard` | Agregaciones para reportes y dashboard. |

## Row Level Security (RLS)

- RLS está **habilitado** en todas las tablas.
- El backend opera con la clave **SERVICE ROLE**, que ignora RLS por diseño.
- Solo existen políticas `SELECT` públicas (`anon`/`authenticated`) para el catálogo
  (`producto`, `categoria` y `sucursal` activos). No hay políticas públicas de escritura.
- Si en el futuro el frontend consulta directamente a Supabase para catálogo, lo hará
  bajo estas políticas de solo lectura.

## Roles de usuario

El campo `rol` en la tabla `usuario` válida los siguientes valores (CHECK):

- `ADMINISTRADOR` — Acceso completo al sistema.
- `ENCARGADO_SUCURSAL` — Gestión de una sucursal específica.
- `VENDEDOR` — Registro de ventas y atención a clientes.
- `INVENTARIO` — Control de inventario y abastecimiento.
- `TIENDA` — Portal de tienda: consulta el catálogo, crea pedidos y visualiza sus propios pedidos.

## Configuración de conexión

La configuración de Supabase se almacena en variables de entorno
(`backend/.env`, ver `backend/.env.example`):

```env
SUPABASE_URL=https://<project-ref>.supabase.co
SUPABASE_PUBLISHABLE_KEY=<anon-key>
SUPABASE_SERVICE_ROLE_KEY=<service-role-key>
JWT_SECRET=juampyzel_secret_key_2024
JWT_EXPIRES_IN=24h
PORT=5000
```

- La clave **SERVICE ROLE** solo se usa en el backend (ignora RLS). Nunca exponer en el frontend.
- La clave **publishable** (anon) puede usarse en el frontend con RLS aplicado.
- El frontend React se comunica con el backend por API REST y no se conecta a la base de datos.

## Cómo aplicar el esquema

1. Crear el proyecto en [Supabase](https://supabase.com/dashboard).
2. Abrir **SQL Editor** y ejecutar el contenido de `supabase/schema.sql`.
3. Copiar `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` y `SUPABASE_SERVICE_ROLE_KEY`
   a `backend/.env`.

También puede aplicarse con el CLI de Supabase: `supabase db push`.
